# 低频执行核验项目：目标与任务重排

> 后续实施采用 `executing-plans` 按任务逐项验收。本文取代旧计划的后续排序，历史完成记录与性能未达标状态保留；本次只调整计划，不修改执行模型或回测逻辑。

**日期：** 2026-11-16。**评估基线：** 2.6.1 / `a5965fd`。

**目标：** 让研究者把已筛选的沪深普通股日/周频策略，在明确的数据与成交假设下，转成可解释、可复验的订单、账户轨迹和约束偏离报告，支持候选策略进入下一阶段的判断。

**架构：** 数据与因子研究、快速账户初筛在上游；本项目承担候选执行近似、规则约束和独立账户核验。现有 `portfolio_signal`、`plan_rebalance`、准备快照与冻结订单入口优先复用。真实用例证明接口不足时再补，不提前扩成完整投研平台、快速矩阵内核或实盘系统。

| 上游与使用闭环 | 数量意图与 CSV 接口已存在；目标权重规划为离线估算，卖款依赖真实成交；通用上游自动对接未验收 | 当前最有价值的缺口是一个完整代表用例，而非更多通用接口 |

上述性能来自对应批次记录，不是本次重新计时。不同数据跨度、委托密度和计时范围不拼成通用加速倍数。原 20 秒冷进程、1 GiB 峰值继续记录为未全面达成的优化目标，不改写为通过；它们不能替代用户工作负载定义，也不是行业实战标准。

## 二、策略指令与账户反馈要分清

| 上游交付 | 当前可复用入口 | 验收要点 |
| --- | --- | --- |
| 已确定时间和数量的指令 | `prepare_order_tape` → `run_order_tape` | 核验这些请求的执行；不自动把失败订单重做成目标权重 |
| 目标权重/调仓目标 | `plan_rebalance` + 账户快照 + 既有回调 | 计划估计不当作实际成交；执行不足如何处理必须先固定政策 |
| 随账户变化的策略规则 | `portfolio_signal` / `run_prepared_backtest` | 后续决策用当时实际现金、持仓、可卖量和可得数据；不能用静态订单带冒充反馈闭环 |

第一版可以选择“一次申报、不追单、下个调仓日再规划”的明确政策，也可以采用实际策略已有政策；不因回测结果临时改变。卖单未成交不得资助后续买入；不足成交应体现为偏离和原因，不伪造成目标仓位已实现。没有必要先新增通用策略语言或动态执行服务。

## 三、重新排列任务

P0 表示缺失会影响用例结论或阻断使用；P1 表示形成可重复交付与提高吞吐；P2 表示有触发证据才开展。性能导致实际任务 OOM、超时或无法批量运行时，直接提升为 P0。

| 顺序 | 优先级 | 任务及产物 | 为什么排在这里 | 验收/退出条件 |
| --- | --- | --- | --- | --- |
| R1 | P0 | 固定一个代表日/周频用例：上游输入、股票池、决策/可得/执行时点、调仓及未成交政策、费用、基准、候选批量和等待预算 | 先定义使用成功，避免以压力测试代替产品需求 | 一页场景说明与可执行输入；优先用实际上游输出，未提供时标明缺口，工程替代不称真实联通 |
| R2 | P0 | 对该用例做数据与模型准入报告：历史池/生命周期、行情与规则、权益、价格口径、可得时间、缺口及成交假设 | 错误输入或假设会让多个账本一起算对错误问题 | 来源与快照可追溯；关键事实缺失阻断相应结论；当前版本历史数据不标 strict vintage PIT；不在引擎内重建整个数据平台 |
| R3 | P0 | 跑通一个真实资金反馈闭环：本地数据 → 上游信号/目标 → 数量计划 → 成交与约束 → 下一次调仓 → NAV/偏离报告，配固定基准 | 验证当前模块能否完成用户工作，而非只完成固定数量回放 | 复用现有入口；覆盖停牌、资金不足、部分成交和至少一个实际权益事件；计划与实际分开，差异有原因。无上游时仅交付明确标注的价格数据工程基线，不假称该项全部通过 |
| R4 | P0 | 补独立预期：对本用例关键资金、费用、T+1、权益和执行时序给人工可核算小场景；保留宽组合吞吐回归 | 默认限流案例说明同引擎多路径对齐仍可能共错 | 先写预期后运行；能解释首个差异；来源不足不强凑“全部正确”，不靠关闭核验通过 |
| R5 | P1 | 把真实用例所需的上下游交付固定下来：复用快照、意图 ID/时间、费用及模型参数、结果归档；有目标权重时明确失败反馈 | 已有接口先落实到调用方，再决定缺什么 | 一条可复跑命令或调用流程；同输入重复建立账户结果一致；只加真实字段与转换，暂不建 RPC/编排/任务平台 |
| R6 | P1 | 统一执行偏离与完整差异报告：委托、成交、拒单、未执行、权益和日终账户；需要时将实验额外比较变成稳定可复用能力 | 让研究者理解为何偏离，而不只读出一个净值或布尔值 | 区分信号、规划、规则、资金、容量与模型差异；保留原 `compare_backtests` 兼容语义，不静默扩大旧 equal 标志含义；不堆无用日志 |
| R7 | P1 | 按 R1 用例做端到端性能验收：加载、准备、重复回放、归档、进程峰值与批量候选总耗时；测真正峰值阶段 | 速度仍重要，但应改善真实研究周转时间 | 同数据/模型/工作量前后对照、记录冷/暖边界；保留 20 秒/1 GiB 的原状态。先诊断再选最小改动；OOM/超时立即升 P0，无稳定收益停止，不为凑数改变成交模型 |
| R8 | P1 | 固定可交付基线：版本/依赖、ABI 失败提示、安装包、源数据要求、用例复验及 CI | 让别人能使用当前成果，不只是本机有实验脚本 | 现有 Windows/Python/NT 组合稳定可安装；一条数据到报告路径可复验；不发布私有行情或凭据。当前 CI/打包继续复用，不启动跨平台重构 |
| R9 | P2 | 复用已有历史竞品实验，选一个独立实现对共同规则场景做更新对账；再决定是否需要换/复用后端 | 独立参照有价值，但全功能竞品集成成本不应压过本用例 | 相同原始数据、信号可得时点、资金及费用，先解释逐笔/逐日差异；缺失功能记为缺失，不替另一框架重写引擎，不用不同模型速度排名；若 R4 缺独立执行预期，可将必要子集前移 |

R1–R4 可以并行准备独立材料，但任何策略有效性结论必须同时通过输入/模型准入与真实闭环。R5/R6 的最小部分可随 R3 一起完成，不等到 P1 才补齐必需交付。

R2/R4 还应检查参与率、滑点和 Bar 路径假设对关键结论的敏感性。OHLC 无法判定的盘中顺序不当作已知事实；结果高度依赖该假设时，缩小结论或补所需粒度的数据，不用合成 L2 名称替代证据。

## 四、暂停与重开条件

| 暂停项 | 什么时候重开 |
| --- | --- |
| 继续寻找 5%–10% 的局部热点、替换原生实时分析器、专门订单索引 | R7 或真实使用证明该项阻塞候选周转；能在不减核验、不依赖脆弱内部修改下验证收益 |
| 新公共列式输入/磁盘缓存/并行调度 | 对象归属和复用次数证明能解决实际内存或重复准备问题，兼容成本值得；不能仅因 Rust/Numba 名称作决定 |
| 更大规模或多年密集压力矩阵 | 真实目标池、持仓宽度、周转或并发需求超过现有证据，或故障指向该维度；不机械扩大所有组合 |
| 融资融券、北交所、完整转债、真实 L2、分钟深化、券商实盘 | 有独立需求、相应数据与独立验收范围；不混入当前普通股低频主线 |
| NT 升级、ABI 重构、跨平台、新后端 | 当前依赖阻断使用，或同规则实测证明目标无法达成；新后端先过差异验收，保持替换可能性 |

正确性回归、已知漏洞/错误修复、关键数据缺口、稳定交付始终保留，不因暂停微优化而停做。
